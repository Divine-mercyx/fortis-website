Fortis CLI · free

Security checks on every push.

The Fortis CLI runs on your laptop and in CI. It's free, needs no account, and stops leaked keys before they leave your machine. It also finds vulnerable packages and risky Docker and GitHub Actions setups.

What it does

Fortis is a command-line tool. Install it in a repository, and it checks your code on every push and every CI run:

Leaked secrets

Paystack, Flutterwave, Monnify and Stripe secret keys, cloud and API keys, tokens, private keys and database passwords. A push containing one is blocked on the laptop.

Vulnerable packages

Known vulnerabilities in your dependencies, from the public OSV database, with the version and command that fix each one.

Supply chain

Docker base images with no version, not pinned, or past end of life, and GitHub Actions that aren't pinned or that run untrusted pull-request code.

Your running app

An OWASP ZAP scan of the app on your own machine, for missing headers, cookie flags and exposed data.

Every finding comes with the file, the line and how to fix it. Secrets are always masked in the output (sk_live_••••d0e4), so reports are safe to paste into CI logs and chat.

Requirements

  • git, for the pre-push hook.
  • Node.js 18.17 or newer, only if you install from npm. The standalone binary, the Python package and the Docker image need no Node.
  • Docker or a local ZAP, only for fortis test.

Builds exist for Linux (x64 and arm64, including Alpine), macOS (Apple silicon and Intel) and Windows (x64).

Install

Pick the one that fits your project. They all install the same CLI.

Add it to the project as a development dependency, so everyone on the team gets the same version:

$npm i -D fortis-watchdog

With pnpm: pnpm add -D fortis-watchdog. Yarn: yarn add -D fortis-watchdog (Plug'n'Play works too). Bun: bun add -d fortis-watchdog. Then run it with npx fortis, pnpm exec fortis, yarn fortis or bunx fortis.

A standalone build, so it needs no Node:

$pip install fortis-watchdog

Or pipx install fortis-watchdog, or uv tool install fortis-watchdog. Install it in your project's .venv or globally: the git hook finds it even when the virtual environment isn't active, and through uv run and poetry run.

For any language. The script puts the binary in ~/.fortis/bin and checks it against the release's checksums:

$curl -fsSL https://github.com/Divine-mercyx/fortis/releases/latest/download/install.sh | sh

FORTIS_VERSION=0.1.0-beta.12 pins a version, and FORTIS_INSTALL_DIR changes the folder. On Alpine, run apk add libstdc++ first.

For any language, in PowerShell:

>irm https://github.com/Divine-mercyx/fortis/releases/latest/download/install.ps1 | iex

It installs to %USERPROFILE%\.fortis\bin and adds that to your PATH. Open a new terminal afterwards.

Nothing to install on the machine. Useful in CI:

$docker run --rm -v "$PWD:/src" -w /src ghcr.io/divine-mercyx/fortis fortis scan --ci

Use a version tag such as ghcr.io/divine-mercyx/fortis:0.1.0-beta.12 to pin it.

Check it works with fortis --version. The examples below write fortis; in an npm project, that's npx fortis.

Quick start

  1. Set up the repository. From its root:
    $fortis init
    This installs the pre-push hook and writes .fortis.json. Commit that file; it holds settings, never secrets.
  2. Scan everything once.
    $fortis scan
  3. Push as usual. The hook checks what you're pushing. A critical finding, such as a live payment key, stops the push and shows the fix. Anything less serious is reported and the push goes through.
  4. Add it to CI so every pull request is checked too. See CI pipelines.
Already have findings you can't fix today? Run fortis baseline once and commit the file it writes. From then on only new findings block. See fortis baseline.

fortis scan

Scans the repository and prints each finding with its fix.

OptionWhat it does
--pre-pushOnly the files in the commits being pushed. The git hook uses this.
--ciA full scan for CI. Turned on automatically when the CI variable is set.
--fail-on <severity>Exit with code 1 at this severity or above: critical (default), high, medium, low or info.
--historyAlso search every commit on every branch for secrets. See Secrets in git history.
--sarif <file>Write SARIF, for GitHub code scanning, GitLab and editors.
--junit <file>Write JUnit XML, for CI systems that show test reports.
--pr-commentIn GitHub Actions or GitLab CI, post one comment on the pull request listing what it adds, and update it in place.
--jsonPrint the results as data. Secrets are masked here too.
--sbom <file>Also check a CycloneDX JSON SBOM, for full Java, Kotlin and Python coverage.
--no-baselineReport and block on every finding, ignoring .fortis-baseline.json.
--offlineNo network: skips the dependency check, unless you pass --osv-db.
--osv-db <dir>Check dependencies against downloaded OSV data. See No internet.
--submodulesAlso scan git submodules, which are skipped by default.
--paths-from <file>Only scan the files listed, one per line (- reads them from stdin).
--no-cacheAsk OSV again instead of using answers cached in the last 6 hours.
Examples
fortis scan                      # everything, report only
fortis scan --fail-on high       # stricter: block on high findings too
fortis scan --history            # include secrets anywhere in git history
fortis scan --ci --sarif fortis.sarif

fortis init

Sets up the current repository:

  • writes .fortis.json;
  • installs the git pre-push hook, keeping any hook you already have;
  • adds a security:scan script to package.json, if there is one.

--no-hook skips the hook. After you upgrade Fortis, run fortis init again to update the hook; your own lines in it are kept.

fortis baseline

Records today's findings in .fortis-baseline.json. Commit it, and from then on only new findings block pushes and CI. This is the easiest way to adopt Fortis in an existing codebase.

Findings are matched by rule, file and the masked line of code, not the line number, so moving code around doesn't make an old finding look new. The file holds fingerprints, never code. Run it again whenever you want to accept the current state.

fortis ci init

Writes a CI pipeline that scans every pull request and push. It detects your CI from the files in the repository, or you choose with --provider: github, gitlab, bitbucket, azure, jenkins, circleci or buildkite. The pipeline needs no secrets. It never overwrites a file you already have; --force replaces one that Fortis wrote. See CI pipelines.

Testing your app locally

Runs an OWASP ZAP scan against an app running on your own machine. It crawls the app and inspects its responses for missing security headers, insecure cookies, exposed data and similar problems. It sends no attacks, and the results stay on your machine.

$fortis test --target http://localhost:3000 --local
OptionWhat it does
--target <url>The app to test: localhost, 127.0.0.1 or *.localhost.
--minutes <n>How long to crawl (default 2).
--wait <seconds>Wait for the app to start answering first.
--fail-on <severity>Exit 1 at this severity or above (default high).
--zap-report <file>Read a ZAP JSON report you ran yourself instead of running ZAP.

ZAP: Fortis uses Docker (the official zaproxy/zap-stable image), or a ZAP installed on your machine when Docker isn't running. To install one, use brew install --cask zap on macOS, sudo snap install zaproxy --classic on Linux, or winget install ZAP.ZAP on Windows. FORTIS_ZAP_PATH points at a specific zap.sh or zap.bat.

Behind login: set FORTIS_ZAP_AUTH to a test user's token, and ZAP tests the pages and APIs behind login too. The token is sent only to the target, passed to ZAP through the environment, and removed from all output. FORTIS_ZAP_AUTH_HEADER=Cookie sends it as a cookie instead.

fortis doctor

Checks the install, the git hook, .fortis.json, network access, git, your lockfiles and Docker, and prints the fix for anything wrong. Start here when something doesn't work.

$fortis doctor

--json prints the results as data, --offline skips the network checks, and --strict also fails on things that are only worth knowing. It exits 1 if something stops Fortis doing its job.

explain and rules

shell
fortis rules                # every rule, with its severity
fortis explain FX-SEC-001   # why a rule matters and how to fix it

fortis update

Updates a binary installed with the install scripts to the latest release, after checking it against the release's checksums. fortis update 0.1.0-beta.12 installs a specific version. If you installed with npm or pip, it tells you the command to use instead.

Once a day, outside CI, Fortis also prints a notice when a newer version exists. Set FORTIS_NO_UPDATE_CHECK=1 to turn it off.

The pre-push hook

fortis init installs a git pre-push hook. When you push, it finds the CLI and runs fortis scan --pre-push on the files in the commits you're pushing. On the first push of a new repository or branch, that's every commit the remote doesn't have yet. So a key committed early and deleted later is still caught.

  • A critical finding blocks the push. Everything else is shown, and the push goes through. Change the threshold with "failOn" in .fortis.json.
  • The hook finds the CLI in node_modules (npm, pnpm, Yarn, including Plug'n'Play, and Bun), in a Python virtual environment, or on your PATH.
  • In an emergency, skip it once with git push --no-verify. CI still scans.

pre-commit, lefthook and Husky

If your team already uses a hook manager, run Fortis through it instead. Install the CLI so fortis is on your PATH, then add one of these.

.pre-commit-config.yaml
repos:
  - repo: https://github.com/Divine-mercyx/fortis
    rev: cli-v0.1.0-beta.12
    hooks:
      - id: fortis

Then pre-commit install --hook-type pre-push.

lefthook.yml
pre-push:
  commands:
    fortis:
      run: fortis scan --pre-push --stdin
      use_stdin: true
.husky/pre-push
npx --no-install fortis scan --pre-push --stdin

--stdin reads the commits git is pushing, so a first push covers every new commit.

CI pipelines

The pre-push hook can be skipped, so check every pull request in CI as well. No key or secret is needed. Run fortis ci init to write the file for your CI, or copy this complete GitHub Actions workflow into .github/workflows/fortis.yml.

.github/workflows/fortis.yml
name: Fortis

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read
  pull-requests: write    # for the pull-request comment
  security-events: write  # for GitHub code scanning

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - name: Install Fortis
        run: |
          curl -fsSL https://github.com/Divine-mercyx/fortis/releases/download/cli-v0.1.0-beta.12/install.sh | FORTIS_VERSION=0.1.0-beta.12 sh
          echo "$HOME/.fortis/bin" >> "$GITHUB_PATH"
      - name: Fortis scan
        run: fortis scan --ci --sarif fortis.sarif --pr-comment
        env:
          GITHUB_TOKEN: ${{ github.token }}
      - name: Upload to GitHub code scanning
        if: always() && hashFiles('fortis.sarif') != ''
        continue-on-error: true  # free on public repositories
        uses: github/codeql-action/upload-sarif@v4
        with:
          sarif_file: fortis.sarif
          category: fortis

What you get:

  • The build fails on a critical finding (change it with --fail-on).
  • Findings appear on the pull request's changed lines as annotations, and in one summary comment listing only what the pull request adds. A pull request from a fork gets a read-only token, so it gets no comment.
  • GitHub code scanning shows them in the Security tab. That's free on public repositories and needs GitHub Advanced Security on private ones; the step never fails the build.

GitLab CI, in .gitlab-ci.yml:

.gitlab-ci.yml
fortis-scan:
  stage: test
  image: ghcr.io/divine-mercyx/fortis:0.1.0-beta.12
  script:
    - fortis scan --ci --sarif fortis.sarif --junit fortis-junit.xml
  artifacts:
    when: always
    paths: [fortis.sarif]
    reports:
      junit: fortis-junit.xml
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH

For a merge-request comment, add --pr-comment and set FORTIS_GITLAB_TOKEN to a project access token with the api scope.

Bitbucket, Azure DevOps, Jenkins, CircleCI and Buildkite: run fortis ci init --provider <name> to write a pipeline for yours. It uses the standalone binary or the Docker image, so your project doesn't need Node, and it needs no secrets.

Secrets in git history

$fortis scan --history

This searches every commit on every branch. A key that was committed and later deleted can still be read by anyone who can clone the repository, so treat it as leaked: rotate it with the provider. Each secret is reported once, at the commit that introduced it. In CI, the checkout needs full history (fetch-depth: 0 in GitHub Actions); fortis ci init --history sets this for you.

Ignoring a finding

When you've reviewed a line and it's safe, add a comment on it, or on the line above, with your reason:

Any language
const testKey = 'sk_test_…'; // fortis-ignore: Paystack test key, safe to commit

// fortis-ignore-next-line: public demo key
const demo = 'pk_live_…';

Any comment style works, such as # fortis-ignore in Python, YAML and Dockerfiles. To skip whole folders, add globs to "ignore" in .fortis.json.

Proxies and no internet

Fortis reads the same proxy variables as curl:

shell
export HTTPS_PROXY=http://proxy.company.local:8080
export NO_PROXY=.company.local,10.0.0.0/8
  • If the proxy inspects TLS with its own certificate, give Fortis the CA with --ca /path/ca.pem, FORTIS_CA_FILE or NODE_EXTRA_CA_CERTS.
  • Answers from OSV are cached for 6 hours in ~/.cache/fortis, so pre-push checks stay quick and keep working if the network drops.

No internet at all: download OSV's data for your ecosystems, copy it across, and point Fortis at the folder:

shell
curl -O https://osv-vulnerabilities.storage.googleapis.com/npm/all.zip   # also PyPI, Maven, Go, NuGet…
fortis scan --offline --osv-db ./osv

Windows

  • Git runs the hook with its own shell, so it behaves the same in Git Bash, PowerShell, cmd and WSL.
  • In GitHub Desktop, VS Code and Visual Studio, a blocked push fails with the Fortis report as the error message. Fix the finding and push again.
  • CRLF line endings, backslash paths and files saved with a byte-order mark are all handled, and a baseline written on Windows matches one written on a Mac or Linux.

Rules

RuleSeverityWhat it finds
FX-SEC-001CriticalPayment-provider secret key in code. A Paystack, Stripe, Flutterwave, Monnify, SeerBit, OPay or Squad secret key, or a Stripe restricted key or webhook secret, in the repository or config. Move it to an environment variable or secret manager, then rotate it with the provider.
SEC-GEN-001HighGeneric secret in code. An API key, token, private key or database password (including in a connection URL or connection string). Covers AWS, Google, GitHub, Slack, SendGrid, OpenAI, Anthropic, npm, PyPI, Supabase, Twilio and many more, plus random-looking values in .env, .properties and YAML files.
DEP-OSVVariesVulnerable dependency. A package with a known vulnerability. Each finding names the version that clears every advisory and the upgrade command for your package manager; for an indirect dependency, the direct one that pulls it in. Severity follows the advisory.
SUP-IMG-001LowDocker base image with no tag or latest, so each build can get a different image.
SUP-IMG-002InfoDocker base image not pinned by digest in a production Dockerfile. Add @sha256:… for the image you tested.
SUP-IMG-003MediumDocker base image past end of life, such as node:16, python:3.7 or debian:buster, so it no longer gets security fixes.
SUP-GHA-001MediumThird-party GitHub Action not pinned to a commit. Whoever controls that repository can move a tag like @v4 and run their code with your workflow's secrets. Actions from GitHub itself aren't flagged.
SUP-GHA-002HighA pull_request_target workflow runs the pull request's code, giving anyone who opens a pull request your repository's secrets and a write token.

Run fortis explain <rule> for the full explanation and fix. Every rule is measured against a labelled benchmark, and a release can't make a rule less accurate.

Files are found in any folder. Development and test dependencies are skipped where they can be told apart. If Fortis can't check something, it says so instead of passing it as clean. That covers a project with no lockfile, a package installed from git, CocoaPods, and C or C++ packages from Conan or vcpkg (OSV has no advisories for those last two).

Build files list only direct dependencies. For full coverage of Java, Kotlin, Scala or a hand-written requirements.txt, commit a lockfile or pass a CycloneDX SBOM with --sbom. On GitHub Actions, fortis ci init adds the SBOM step for Maven, Gradle and Python.

.fortis.json

Commit it. It never holds secrets, and every setting is optional.

.fortis.json
{
  "$schema": "https://cdn.jsdelivr.net/npm/fortis-watchdog/fortis.schema.json",
  "failOn": "critical",
  "ignore": ["legacy/**", "**/*.generated.ts"],
  "target": "http://localhost:3000"
}
SettingWhat it does
failOnThe severity that blocks a push or fails a scan (default critical).
ignoreGlobs for paths to skip.
targetThe default URL for fortis test.
$schemaGives your editor autocomplete. fortis init adds it.

A misspelled setting isn't silently ignored: Fortis warns and suggests what you meant. These are always skipped: node_modules, vendor, dist, build, coverage, minified files, source maps, binaries and files over 1 MB.

Exit codes

CodeMeaning
0Passed: nothing at or above the threshold.
1Findings at or above the threshold. The push or build should stop.
2Couldn't run: a bad option or setting, no files found, neither Docker nor ZAP available, or a network error.

What leaves your machine

  • Your code never does. Every check runs on your laptop or in your own CI. Without a key, the CLI sends nothing to Fortis; fortis doctor only checks that it could reach the Fortis API.
  • Dependency check: package names and versions go to the public OSV database (api.osv.dev). --offline or --osv-db keeps this local too.
  • Update notice: once a day, outside CI, Fortis asks GitHub what the latest release is. It sends nothing about your project, and FORTIS_NO_UPDATE_CHECK=1 turns it off.
  • Pull-request comments go to your own GitHub or GitLab, with your CI's token. They show the rule, file and line, never the code.
  • fortis test talks only to the app you point it at.

Troubleshooting

Start with fortis doctor. It finds most of these and prints the fix.

"Fortis: the CLI isn't installed in this repo"
The git hook couldn't find the CLI. Install it in the project (see Install) or globally, for example npm i -g fortis-watchdog. To push once without the check: git push --no-verify.
The hook didn't run
Run fortis init again. If you use a custom core.hooksPath, such as Husky's, Fortis installs into that folder.
"found but no lockfile, so those dependencies weren't checked"
Fortis needs exact versions. Commit the lockfile the message names. Bun lockfiles aren't read yet; pass a CycloneDX SBOM with --sbom instead.
"Dependency check skipped: could not reach api.osv.dev"
Allow https://api.osv.dev through your proxy or firewall (see Proxies), or use --osv-db. Until then, the scan says "the dependency check did not finish" rather than passing.
"Docker is installed but not running"
Start Docker Desktop or the docker service, or install ZAP locally (see fortis test).
A finding is wrong
Add fortis-ignore with a reason (see Ignoring a finding), and please tell us with a made-up example, so we can fix the rule.
